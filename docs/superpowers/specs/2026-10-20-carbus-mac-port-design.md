# CarBUS for Mac — дизайн порта (v1)

Дата: 2026-10-20. Статус: **утверждён** (2026-10-20).

## 0. Подтверждено при утверждении

- **Расположение проекта**: `~/dev/canH/carbus-mac`, инициализируется как git-репо.
- **Трейсы**: файлами на маке, в примонтированной с хоста папке `./traces`.
- **CAN-FD**: v1 — классический CAN (прибор пользователя классический). FD-пути в
  коде сохраняем, но отдельную FD-вкладку в v1 не делаем.
- Остальные «калы исполнителя» из §9 приняты как есть.

## 1. Зачем это и почему сейчас

У пользователя есть программатор **CAN-Hacker v3.2** (в приборе рапортуется как
`HW_CH32`, прошивка `2.2.3.57`, серийник `6950`/`0x1B26`, каналы `1=CAN, 2=CAN,
3=LIN`). Штатный софт **CarBUSAnalyzer** — только под Windows. У пользователя Mac.

Нужен инструмент под Mac, который воспроизводит тот рабочий цикл, которым человек
реально пользуется для реверса авто-шин и разработки прошивок на МК:

- живой мониторинг CAN — видеть, **какие биты/сообщения меняются**, когда жмёшь
  кнопку (на руле и т.п.);
- запись трейсов и просмотр/воспроизведение;
- передача кадров в шину (как в десктопе — решение «что и как слать» принимается
  в самом интерфейсе).

Форма поставки по требованию пользователя: **веб-GUI + бэкенд, завёрнутые в
Docker**, «склонировал — запустил контейнер». Не нативное приложение.

## 2. Ключевое открытие, снимающее главный риск

Протокол прибора **не нужно реверсить**. На PyPI есть библиотека
**`carbus-lib`** (MIT, `github.com/controllerzz/carbus_lib`), которая уже
реализует протокол CAN-Hacker / Car Bus Analyzer, «протокол версии 22» — ровно
прошивка этого прибора.

Проверено спайком на этом же приборе на Mac (изолированный venv, только чтение):
`CarBusDevice.open()` → `get_device_info()` → `open_can_channel(500k,
listen_only)` → приём → `close()` отработали end-to-end. `device_info` корректно
вернул `HW_CH32 / 2.2.3.57 / serial 6950 / {1:CAN,2:CAN,3:LIN} / gateway=True`.
(0 кадров — потому что прибор был просто в USB, не на живой шине; это ожидаемо.)

Библиотека даёт: открытие CAN/CAN-FD канала и битрейты, аппаратные фильтры,
терминатор 120 Ω, приём (очередь/`receive_can_on`/хуки `on_can_id`/`on_can_match`/
`CanIdRouter`), `send_can`, `PeriodicCanSender`, ISO-TP и UDS (на будущее),
`get_device_info()`. Транспорты: локальный COM, **TCP-мост**, и relay через
публичный сервер.

## 3. Жёсткое ограничение платформы (определяет архитектуру)

**Docker Desktop на macOS не видит USB/serial.** Контейнеры крутятся в скрытой
Linux-VM, куда macOS не прокидывает USB-устройство (`--device` работает только на
Linux-хосте; USB/IP из коробки нет). Значит код **внутри контейнера физически не
дотянется** до `/dev/cu.usbmodem…`. Вывод: один тонкий нативный компонент на маке
обязан держать порт. Используем **штатный TCP-мост `carbus-lib`**, свой код для
моста не пишем.

## 4. Архитектура (решено)

```
[CAN-Hacker v3.2]
    │ USB CDC-ACM  → /dev/cu.usbmodem…  (драйверы не нужны)
    ▼
[Мак, НАТИВНО] python -m carbus_async.tcp_bridge --serial /dev/cu.usbmodem… --port 7000
    │ TCP (локально, host.docker.internal)
    ▼
[Docker-контейнер] Python-бэкенд (FastAPI + uvicorn + websockets) на carbus-lib
    │   CarBusDevice.open_tcp("host.docker.internal", 7000)
    │   — сессия CAN, агрегация монитора, запись/чтение трейсов, передача, фильтры
    │ HTTP (отдаёт SPA) + WebSocket (живые данные и команды)
    ▼
[Chrome на маке] тонкий веб-клиент: монитор / поток / bit-map / передача / трейсер
```

- Единственная нативная часть на маке — официальный `tcp_bridge` (одна команда).
- Публичный relay `carbus-lib` (`185.42.26.80`, пароль из примеров `1234`)
  **не используется никогда**; трафик шины наружу не уходит.
- Мост слушает только локально и доступен контейнеру через `host.docker.internal`;
  на LAN/в интернет не публикуется.

## 5. Состав v1 (цели)

Паритет по ядру с десктопом, где это осмысленно. **Реальный интерфейс десктопа
восстановлен из Delphi-форм бинарника** — см. `docs/reference/carbus-dfm/UI_MAP.md`
(и 65 `*.dfm.txt` рядом); порт ориентируется на него, а не на пересказ.

Общая раскладка главного окна (из `frmMain`): верхний тулбар (Connect, Channel
options, Gateway, Clear, Stream, Tracer, Transmit, Filter, Logs) · центральная
область приёма с вкладками **Receive** / **Separate receive** · док передачи снизу
с вкладками **CAN / LIN / FD Transmit** · панель фильтров/шлюза справа · статусбар.

1. **Подключение**: выбор цели моста (хост:порт), режим устройства, битрейт на
   канал (пресеты + произвольный), Connect/Disconnect; панель `device_info`
   (железо/прошивка/серийник/каналы/фичи). Режим **normal по умолчанию**,
   **listen-only — переключаемая опция** (не принудительная).
2. **Живой монитор (Receive Monitor)**: в десктопе это кастомный `TDrawGrid`,
   сгруппированный по ID, обновление значений **на месте**; для порта — таблица с
   колонками `CH, ID (hex, 11/29 бит), DLC, байты данных, счётчик, период/Δt,
   направление` и **подсветкой изменившихся байт/бит**. Разнесение каналов
   (вкладка Separate receive / Group by channel). Контекстные действия как в
   оригинале: View bit-map, Show message signals, Set comment, **Copy message to
   TX-List**, Add message ID to filter, Message ID in HEX, Clear protect bits,
   Sort, Group by channel. Тулбар: Monitor/Stream switch, **Record/Pause**,
   **Set marker/breakpoint**, Monitor rarely changing data, Move trace to Tracer.
3. **Bit-map одного ID** (`frmDetails`): каждый байт — строка из 8 бит с колонками
   `x80 x40 x20 x10 x08 x04 x02 x01` + десятичное значение байта + комментарий;
   **подсветка меняющихся бит** — главная фича «смотреть, что меняется при нажатии».
4. **Поток (Stream)**: хронологический лог кадров, пауза, фильтр по ID.
5. **Передача (Transmit)** (`frameCANTasks`): список задач; `Add`, `Shot`
   (однократно), `Run` (периодически с периодом), `Run All` / `Stop All`,
   сохранение/загрузка списка; на задачу — флаги `29 bit`/`RTR`, редактор данных
   (8/64 байта), канал. **Триггеры**: авто-отправка кадра по приёму заданного
   `ID`+`DLC`+`Data` на канале (`Trigger`/`Delay (ms)`/`Trigged action`). Бэкенд:
   `send_can` / `PeriodicCanSender` / хуки `on_can_match` для триггеров.
6. **Фильтры**: аппаратные (`set_std_id_filter`/`set_ext_id_filter`/
   `clear_all_filters`, разметка индексов канал1 0–12 / канал2 13–28) и
   программный Range (From/To/Exclude).
7. **Запись и воспроизведение трейсов**: запись потока в файл (старт/стоп),
   **Tracer** — Play/Stop/Step/Repeat, «Only for Channel», «To Monitor» (показ без
   физической отправки), задержка между кадрами. Тайминги кадров берём из
   **аппаратных меток времени прибора**.

## 6. Не-цели v1 (сознательно вне рамок)

DBC-менеджер; JS-движок (ChakraCore-скрипты); **CAN Bomber / bruteforce**; GUI
для UDS/ISO-TP (библиотека умеет, но без экрана в v1); **LIN-канал (ch3)**;
CAN-шлюз CAN1⇔CAN2; нативная/десктопная упаковка; многопользовательский режим и
авторизация; любой публичный relay / удалённый доступ.

## 7. Анти-цели (провал, даже если «технически работает»)

- Заставлять пользователя реверсить или вручную поддерживать протокол прибора —
  этим владеет `carbus-lib`.
- Монитор, который **лагает/морозит UI** под нагрузкой шины. Обязательно:
  агрегация по ID на бэкенде + вирт. список на фронте; поток парсится вне UI-потока
  браузера (бэкенд шлёт уже готовые дельты).
- Потеря кадров или **враньё по времени** в трейсах. Метки — от прибора; если
  данных нет, помечаем явно, не выдумываем.
- Делать передачу «страшной»/загороженной сильнее, чем в десктопе — решение
  принимает пользователь в интерфейсе.
- Гонять трафик шины через сторонний сервер.

## 8. Ограничения

- Docker-на-маке не видит USB → нативный мост обязателен; это документируется как
  одна команда и оборачивается в простой запуск.
- Прибор этого пользователя — **классический CAN** (линия 2.2.x), 2×CAN + LIN, без
  CAN-FD. v1 целится в классический CAN; FD-пути в коде не выпиливаем, но и не
  требуем (на случай будущего железа CH-4FD).
- `carbus-lib` — async Python (pyserial-asyncio), Python ≥ 3.10. Образ бэкенда
  **пиним на заведомо рабочую версию Python** (предлагается 3.12).
- Целевой браузер — **Chrome** (пользователь согласен). Технически не обязателен,
  но ориентируемся на него.

## 9. Решения «как именно» (мои калы как исполнителя)

- **Бэкенд**: Python 3.12, FastAPI + uvicorn, websockets; `carbus-lib`; к прибору —
  `CarBusDevice.open_tcp("host.docker.internal", 7000)`.
- **Фронт**: лёгкий SPA на Vite + TypeScript; конкретный микрофреймворк (Svelte или
  React) и библиотека вирт. таблицы — на усмотрение исполнителя. Браузер рендерит
  готовые данные, тяжёлой логики в нём нет.
- **Канал данных браузер↔бэкенд**: WebSocket для живого (дельты монитора, поток,
  bit-map) ; REST/WS для команд (connect, transmit, filters, tracer).
- **Темп обновления монитора**: бэкенд коалесцирует состояние по ID и шлёт дельты с
  фиксированной частотой (~20–30 Гц) независимо от скорости шины — плавный UI без
  затопления.
- **Формат трейса**: собственный (JSON-lines или компактный бинарь) с полями
  `ts, channel, id, ext, dlc, data, dir`. Файлы трейсов — в **смонтированной с
  хоста папке**, чтобы лежали на маке и переживали контейнер.
- **Упаковка**: `docker compose` с сервисом бэкенда; обёртка `run-bridge.sh` для
  мака, запускающая `tcp_bridge` через `uv`/`pipx` без ручного venv; README с
  двухшаговым запуском (мост на маке → `docker compose up`).

## 10. Оставлено исполнителю

- Выбор микрофреймворка фронта и либы вирт. таблицы.
- Точные схемы WS-сообщений и формата файла трейса.
- Детали взаимодействия bit-map (как именно подсвечивать/гасить изменившиеся биты).
- Точная раскладка аппаратных фильтров `carbus-lib` ↔ UX.
- Полировка лаунчера моста на маке.

## 11. Риски и как сняты

- Протокол прибора → снят `carbus-lib` + спайк на реальном железе.
- USB в Docker на маке → снят штатным `tcp_bridge` (нативно на маке).
- Производительность живого монитора → коалесценция на бэкенде + вирт. список.
- Точность времени трейсов → аппаратные метки прибора.
- Остаточный риск: совместимость pyserial-asyncio с конкретной версией Python в
  образе → пиним Python 3.12 и проверяем в первом же прогоне бэкенда.
