# CarBUS for Mac — устройство и разработка

Как программа устроена внутри и как с ней работать разработчику. Что умеет интерфейс —
в [руководстве пользователя](user-guide.md), история решений этапа 1 — в
`docs/superpowers/plans/2026-10-20-desktop-parity-rulings.md`.

## Схема

```
[CAN-Hacker v3.2 / HW_CH32]
    │ USB CDC-ACM → /dev/cu.usbmodem…  (драйверы не нужны; VID:PID 0483:5740, «CAN-Hacker v3.2 …»)
    ▼
[Мак, нативно]  run-bridge.sh → python -m app.bridge (127.0.0.1:7000, только pyserial)
    │   находит CAN-Hacker по USB-описателям; LIST — список портов, OPEN — порт прибора
    │ TCP, только 127.0.0.1 (контейнер видит хост как host.docker.internal)
    ▼
[Docker]  backend: FastAPI + uvicorn, carbus-lib
    │   devices.py: что видно (мост + свой USB) → выбор прибора → CarbusSession → протокол прибора
    │   один Hub на процесс: сессия к прибору, монитор, поток, лог, передача, фильтры, отладчик
    │ HTTP (статика фронта, /api/files) + WebSocket /ws (события и команды), 127.0.0.1:8000
    ▼
[Chrome]  frontend: Preact + signals, виртуальные таблицы, реестр действий, хоткеи
```

Docker Desktop на macOS не прокидывает USB в Linux-VM (прямого проброса нет, USB/IP для
USB-serial на маке не работает), поэтому порт прибора держит нативный мост
`backend/app/bridge.py` — небольшой процесс на pyserial, который сам находит CAN-Hacker и
перекладывает байты. Всё остальное живёт в контейнере и не зависит от железа: бэкенд
работает через абстракцию `CanSession`, реальная реализация — только `carbus_session.py`.

На **Linux** USB можно пробросить в контейнер (`docker-compose.usb.yml`): тогда бэкенд
видит порт прибора сам и открывает его напрямую, мост не нужен. **Без Docker** то же
самое запускается прямо на маке: `python -m app.demo` (демо-источник кадров вместо
прибора) или `uvicorn app.server:app` — бэкенд на маке видит USB сам, мост ему не нужен
(если мост тоже запущен, прибор в списке один — через USB напрямую).

## Поиск прибора и мост

**Что считается прибором** (`app/usbports.py`, общий для моста и бэкенда). Порты только
перечисляются (pyserial `list_ports`), ни одного байта в них не уходит. CAN-Hacker v3.2
на маке — `/dev/cu.usbmodem00000000001A1`, VID:PID `0483:5740`, производитель
«Spectratek», USB-строка `CAN-Hacker v3.2 0000000000001B26 2.2.3.57 A06021201`: модель,
серийный номер прибора в hex (0x1B26 = 6950 — тот же, что в «Информации об устройстве») и
прошивка. Вид порта: `canhacker` — имя CAN-Hacker или производитель Spectratek;
`compatible` — VID:PID «виртуального COM-порта» STM32 без имени (по нему ищет приборы и
десктоп, но его же носят чужие платы); `other` — всё остальное (служебные порты мониторов,
плат, телефонов). Порты без USB (Bluetooth, debug-console) не показываются; в контейнере
проброшенный `ttyACM*`/`ttyUSB*` без описателей предлагается как `compatible`.

**Мост** (`python -m app.bridge`, его запускает `run-bridge.sh` в своём окружении с
pyserial и pyserial-asyncio тех же версий, что у бэкенда; Python 3.9+ — подходит и
системный `python3` macOS). Протокол — строки JSON:

1. Клиент подключается и молчит; через 0,1 с мост шлёт приветствие
   `{"bridge": "carbus", "version": 1}`. Если по адресу слушает что-то другое (прежний
   `tcp_bridge` из carbus-lib, «Приёмник AirPlay» на порту 7000), приветствия не будет —
   клиент закроет соединение, не отправив ни байта, и в прибор через чужой мост ничего не
   уйдёт.
2. `LIST` → `{"ok": true, "ports": [...]}` — порты с видом, серийным номером, прошивкой и
   флагом `busy` (порт открыт другим подключением); соединение закрывается. Порты при этом
   не открываются.
3. `OPEN <порт|auto>` → `{"ok": true, "port": {...}}`, дальше по тому же сокету сырые байты
   протокола прибора в обе стороны; или `{"ok": false, "error": "…"}`. Мост открывает
   только `canhacker`/`compatible` или порт, заданный явно (`CARBUS_SERIAL` → `--serial`);
   `auto` — единственный найденный CAN-Hacker. Порт открывается эксклюзивно, на время
   подключения; занятый порт мост ждёт до 1,5 с (прошлое подключение ещё закрывается),
   потом отказывает.

Клиент, который сразу шлёт байты протокола прибора (`CarBusDevice.open_tcp` из
carbus-lib), приветствия не ждёт: мост видит данные раньше 0,1 с и работает как прежний
`tcp_bridge` с `auto`. В консоль мост пишет найденные при запуске приборы, подключения и
отключения, а также когда CAN-Hacker вставили в USB или выдернули.

**Снимок приборов** (`app/devices.py`): `discover` собирает свои USB-порты бэкенда
(`source: "usb"`) и порты моста (`source: "bridge"`, адрес — из «Настроек устройства»);
прибор, видный обоими путями, остаётся один — через USB напрямую. Снимок несёт состояние
моста (`ok` / `down` — никто не слушает / `foreign` — отвечает не мост / `off` — демо),
команду запуска моста для Терминала мака (`bridge.command`: `cd <папка> && ./run-bridge.sh
[порт]`, папка `bridge.project_dir` — из `CARBUS_HOST_DIR`, её задаёт docker-compose; без
неё команда один раз клонирует проект с GitHub в `~/CarBusMac`) и готовую подсказку `hint`,
если CAN-Hacker не найден. Интерфейс по снимку решает, что показать в «Что сделать»
(`setupHelp` в `deviceModel.ts`): в Docker без моста — эту команду с кнопкой «Копировать»,
при работающем мосте без прибора — «вставьте прибор в USB». `pick` выбирает прибор: явно
выбранный в диалоге (ключ `bridge:/dev/…` или `usb:/dev/…`; если тот же порт теперь
виден другим путём — его) или, если выбора нет, единственный CAN-Hacker; несколько —
ошибка «выберите нужный».

**Хаб** опрашивает приборы каждые 2 с, пока открыт интерфейс (как таймер списка
источников в десктопе, 500 мс), и рассылает событие `devices` только при изменении;
`connect` перед подключением берёт свежий снимок. Демо-сервер отдаёт один ненастоящий
CAN-Hacker (`source: "demo"`).

## Безопасность

- Бэкенд и мост слушают только loopback мака; публичный relay `carbus-lib` не используется.
- Мост открывает только порты, распознанные как CAN-Hacker (или заданные явно через
  `CARBUS_SERIAL`), и только из своего списка USB-портов: ни путь к файлу, ни служебный
  порт монитора или платы через него не открыть. Список портов строится без их открытия.
- До localhost может достучаться любая страница, открытая в том же браузере, поэтому
  сервер принимает только запросы с loopback-именем в `Host` (защита от DNS-rebinding), а
  WebSocket и изменяющие HTTP-запросы с чужим `Origin` отклоняет — чужой сайт не может ни
  слать кадры в шину, ни писать файлы (`backend/app/server.py`).
- Загрузка файла с компьютера ограничена 256 МБ; имена файлов — только basename с
  разрешённым расширением (`hub.safe_name`).
- Очередь исходящих сообщений каждой вкладки ограничена (5000): зависшая вкладка
  отключается и получит свежий снапшот при переподключении.

## Бэкенд (`backend/app`)

| Модуль | За что отвечает |
|---|---|
| `models.py` | `CanFrame`: канал, ID, данные, флаги, `timestamp` (с) и `ts_source` (`device` / `arrival`), `direction` (`rx` / `tx`) |
| `can_session.py` | протокол `CanSession` (connect, device_info, open_channel, send, фильтры, терминатор, `frames()`) и `FakeSession` для тестов |
| `usbports.py` | перечисление USB-портов и распознавание CAN-Hacker по USB-описателям (модель, серийный номер, прошивка из USB-строки); общий для моста и бэкенда, только stdlib + pyserial |
| `bridge.py` | нативный мост (`python -m app.bridge`): приветствие, `LIST`, `OPEN`, перекладка байтов, совместимость с клиентами старого образца; и клиентская часть для бэкенда — `bridge_list`, `bridge_open` (`BridgeDown` / `BridgeForeign` / `BridgeRefused`) |
| `devices.py` | снимок приборов (свой USB + мост, без повторов, подсказка «почему не найден») и выбор прибора для подключения |
| `carbus_session.py` | адаптер к `carbus-lib`: транспорт открывает сам — `OPEN` через мост или порт напрямую (`CarbusSession.usb`) — и отдаёт потоки библиотеке; SYNC, терпимый к кадрам прошлой сессии; пресеты и свой тайминг (`CanTiming`), аппаратные фильтры, терминатор; таймауты подключения (5 с) и команд (3 с) — библиотека своих не ставит; обрыв (конец цикла чтения библиотеки) → `ConnectionError` «прибор отключён от USB…»; метки прибора → шкала хоста через `devclock.py`. Опирается на внутренности `CarBusDevice`, поэтому `carbus-lib==0.1.9` закреплена |
| `devclock.py` | перевод 32-битной метки прибора (мкс, переполнение ~71,6 мин) во время хоста: минимальное смещение, подстройка под уход кварца, развёртка переполнения по часам хоста |
| `demo.py` | `DemoSession` — источник кадров, похожий на живую шину (счётчики, редко меняющийся байт, 29-битный ID, второй канал, ответ «ЭБУ» на 0x7E0), и точка входа `python -m app.demo`. Ведёт себя как прибор там, где это важно бэкенду: свободный счётчик меток со случайным стартом, аппаратные фильтры, закрытый канал и «Только слушать», терминатора нет (как у CH32) |
| `hub.py` | одно состояние на процесс: клиенты WS, команды `_cmd_*`, события, тик 40 мс, конвейер приёма, хранилище |
| `monitor.py` | агрегация по (канал, ID, 11/29): последнее значение, счётчик, период, маска изменившихся байт, `stable_ms` для редких данных, агрегатор уникальных payload (колонка FC) |
| `capture.py` | буфер потока: колоночное хранение (`array` + `bytearray`), запись/пауза, метки, выдача диапазонов строк, лимит 5 000 000 кадров |
| `tracefmt.py` | форматы `.trc` v3 (восстановлен из бинарника десктопа) и `.jsonl`, чтение/запись `TraceDoc` |
| `logger.py` | фоновое логирование: `.trc.part` → `.trc` по маске имени, метаинформация, пустые логи удаляются; `recover_parts` при старте сервера собирает `.trc` из брошенного `.part` |
| `transmit.py` | задачи передачи: одиночная, цикл с периодом, счётчики, триггеры по принятому кадру (Одиночный / Старт / Стоп с задержкой) |
| `filters.py` | аппаратные слоты (раскладка и тип слота 11/29 бит из `filters_info` прибора; раскладка сохраняется вместе со слотами) и программные диапазоны с исключениями |
| `tracer.py` | документ трейса (строки, флаги разрешения, точки останова, паузы, начало/конец, таблица ID) и проигрыватель (в шину или в монитор, паузы по меткам или фиксированные, цикл, выделение, шаг) |
| `deskfmt.py` | файлы десктопа кроме трейсов: комментарии `.cmt`, списки передачи `.tsk` |
| `settings.py` | настройки приложения: значения по умолчанию, диапазоны, слияние патча |
| `store.py` | JSON-файлы в `data/` с атомарной записью; битый файл не роняет запуск |
| `schemas.py` | сериализация строки монитора для WS (зеркало `frontend/src/core/types.ts`) |
| `server.py` | FastAPI: `/ws`, `/api/files/{kind}/{name}` (скачать) и `POST /api/files/{kind}?name=` (загрузить), статика `frontend/dist`, guard по Host/Origin, фабрика сессии (USB напрямую или мост — по выбранному прибору) и поиск приборов |

**Hub.** При старте читает `settings`, `comments`, `bitrates`, `connection`, `transmit`,
`filters`, `tz` из `data/` (список передачи и фильтры — если включено восстановление;
файл не того вида — значения по умолчанию, сервер не падает; при чтении ничего не
перезаписывается). Новый WS-клиент получает `hello` — полный снапшот (статус, настройки,
комментарии, подключение, найденные приборы, скорости, строки монитора, состояние потока,
задачи, фильтры, отладчик). `connect` сохраняет конфиг и рассылает его событием
`connection`, закрывает старую сессию, выбирает прибор по свежему снимку (`devices.pick`),
открывает новую сессию к нему, открывает каналы с `auto_open`, сбрасывает и
заново применяет включённые аппаратные слоты (отказ прибора по слоту — предупреждение, а
не сорванное подключение), стартует читатель кадров и, если включено, фоновый лог; смена
скорости — только через переподключение (протокол прибора не закрывает отдельный канал).
Обрыв читателя переводит статус в `error` с текстом `Приём остановлен: …`, не роняя сервер.

Долгие команды (`connect`, `capture_save`, `capture_load`, `capture_to_tracer`,
`tracer_open`, `tracer_save`, `devices_scan`, `capture_frames` — `BACKGROUND_COMMANDS`) выполняются фоновыми задачами: сокет
вкладки принимает следующие команды, не дожидаясь их. `disconnect` и новый `connect`
отменяют висящее подключение. Файлы трейсов читаются и пишутся в отдельном потоке
(`asyncio.to_thread`) по снимку данных — запись потока, передача и воспроизведение в это
время не встают. Передача в закрытый канал или в канал «Только слушать» отклоняется
(прибор молча выбросил бы такой кадр). Вставка и удаление строк отладчика останавливают
проигрыватель.

**Конвейер приёма**: кадр → программные фильтры → монитор → буфер потока → фоновый лог →
триггеры передачи → отладчик («остановить при получении данных»). Наши Tx-кадры (передача,
отладчик в канал) попадают в поток и лог с направлением `tx` и временем хоста в момент
отправки.

**Тик 40 мс** (25 Гц): `monitor_delta` только с изменившимися строками, `capture_tail`
(число кадров, длительность и последние 100 строк — таблица потока догоняет хвост),
`tx_counts` не чаще 4 раз в секунду и только при изменении, `stats` (rx/tx кадров в
секунду) раз в секунду, прогресс отладчика во время игры — не чаще тика. Высокая загрузка
шины не затапливает UI: монитор коалесцирует состояние по ID между тиками.

**Время.** Весь поток идёт по одной шкале — часам хоста (`time.monotonic`). Метку прибора
(32-битный счётчик мкс) сессия переводит в неё (`app/devclock.py`): время = метка +
смещение, смещение — наименьшее наблюдённое «время получения − метка» (метка плюс
минимальная задержка доставки), медленно подстраивается под уход кварца прибора.
Промежутки между принятыми кадрами — точные, по меткам прибора; переполнение счётчика
разворачивается по часам хоста, поэтому паузы в шине любой длины и переподключение
посреди записи время не ломают. Кадры Tx получают время хоста в момент отправки; если
прибор метку не дал — время получения (`ts_source="arrival"`). В `.trc` время пишется
неубывающим (формат хранит секунды по модулю 60). Время в таблицах — секунды от первого
кадра потока/трейса. Местное время для имён логов и `$LocalTime` (время начала записи) —
по часовому поясу браузера (команда `client_tz`, пакет `tzdata` в образе).

## Протокол WebSocket (v2)

Команда клиента — `{"type": "...", "req_id"?: n, ...}`; ответ — `{"type": "reply",
"req_id", "ok", "data" | "error"}` (без `req_id` ошибка уходит событием `error`).
Невалидный ввод не рвёт сокет. Один клиент — одна очередь исходящих.

| Группа | Команды |
|---|---|
| Прибор | `connect {config}` (`config.device` — ключ прибора из снимка или `""` — единственный найденный CAN-Hacker), `disconnect`, `devices_scan {bridge_host?, bridge_port?}` (снимок приборов сейчас; по сохранённому адресу моста он же расходится событием `devices`), `channel_terminator {channel, enabled}`, `bitrates_set {bitrates}`, `client_tz {tz}` |
| Монитор и комментарии | `monitor_clear`, `monitor_frames {ch, id, ext}`, `comment_set {id, ext, text}`, `comments_clear`, `comments_save {name, format}`, `comments_load {name, append}` |
| Настройки | `settings_set {patch}` |
| Поток | `capture_record {on}` (после `capture_load` — новая запись: буфер из файла убирается), `capture_clear`, `capture_rows {start, count}`, `capture_marker {label, comment, auto}`, `capture_save {name, format}`, `capture_load {name}`, `capture_to_tracer`, `capture_frames {ch, id, ext}` (различные payload ID по буферу потока — «Данные сообщения» в режиме потока; считается в отдельном потоке) |
| Передача | `tx_upsert {task}`, `tx_delete {id}`, `tx_clear`, `tx_send {id}`, `tx_start {id}`, `tx_pause {id}`, `tx_start_all`, `tx_pause_all`, `tx_reset {id|null}`, `tx_save {name, format}`, `tx_load {name}` |
| Фильтры | `hw_set {slot}`, `filters_add_id {channel, id, ext}`, `range_upsert {filter}`, `range_delete {id}`, `hw_save {name}`, `hw_load {name}` |
| Отладчик | `tracer_new`, `tracer_open {name}`, `tracer_save {name, format}`, `tracer_rows {start, count}`, `tracer_ids`, `tracer_ids_set {keys, enabled}`, `tracer_find {key}`, `tracer_row_add {row, after?}`, `tracer_row_edit {pos, row}`, `tracer_bounds {which, pos}`, `tracer_rows_delete {positions}`, `tracer_rows_enable {positions|key, enabled}`, `tracer_bp {pos, on?}`, `tracer_bp_clear`, `tracer_comment {pos, text}`, `tracer_config {patch}`, `tracer_play {selection?}`, `tracer_pause`, `tracer_stop`, `tracer_step` |
| Файлы | `files_list {kind}` (`traces` или `lists`) |

Строки отладчика адресуются **позицией среди видимых** (`pos`): неотмеченные в таблице ID
строки скрыты, бэкенд переводит позиции в индексы документа. `tracer_state` несёт `rev`
(позиции сдвинулись — клиент сбрасывает кэш и выделение), `data_rev` (поменялось только
содержимое — перечитать видимые) и `gen` (открыт другой трейс — сбросить подсветку «Найти
сообщения»). Ответы `tracer_row_add`, `tracer_row_edit` и `tracer_rows_delete` несут `rev`
после правки и `pos` — строку для курсора (вставленную, следующую за удалёнными). Пауза,
вставшая сама, объясняется в `tracer_state` / `tracer_progress`: `reason` — `"bp"` или
`"rx"`, для приёма `rx {ch, id, ext}` — принятый кадр.

События сервера: `hello`, `status` (состояние, `device_info`, `device` — прибор подключения из снимка, каналы, файл лога), `connection` (конфиг после `connect`), `devices` (снимок приборов: список, состояние моста, подсказка; только при изменении), `monitor_delta`,
`monitor_reset`, `capture_state` (запись, число кадров, метки, `loaded` — имя файла загруженного потока, `dirty` — есть несохранённое), `capture_tail`, `tx_state`, `tx_counts`, `filters_state`,
`settings`, `comments`, `bitrates`, `tracer_state`, `tracer_progress`, `stats`, `toast`, `error`.
Точные поля — `frontend/src/core/types.ts`.

## Фронтенд (`frontend/src`)

Preact + `@preact/signals`, сборка Vite, тесты Vitest (+ `@testing-library/preact`,
happy-dom), иконки `lucide-preact`. Тяжёлой логики в браузере нет — он рисует готовые данные.

| Папка | Содержимое |
|---|---|
| `app/` | каркас окна: `App` (слои: диалог, плавающие окна, меню, уведомления), `MainMenu`, `MainToolbar`, `Workspace` (слоты панелей и сплиттеры), `StatusBar`, `shellActions` (подключение, виды, панели), `ui.ts` (раскладка в localStorage, хост диалогов и плавающих окон) |
| `core/` | `ws.ts` (клиент протокола: события по типам, команды с `req_id` и таймаутом 10 с; без связи команда сразу отклоняется, очередь — только пока сокет открывается, при обрыве она очищается — отклонённая команда позже на шину не уйдёт; переподключение с паузой 0,25–5 с), `client.ts` (долгим командам — `connect`, сохранение/загрузка трейсов, перенос в отладчик — таймаут 3 мин), `store.ts` (сигналы состояния; `applyEvent` раскладывает события сервера), `types.ts`, `actions.ts` (реестр действий), `hotkeys.ts` (буквы — и в русской раскладке, по `e.code`), `format.ts` (запятая в дробях, разбор HEX), `theme.ts` (тема кэшируется в браузере и ставится скриптом в `index.html` до загрузки приложения — без мигания), `timezone.ts`, `devices.ts` (подписи найденных приборов — общие для статусбара и «Настроек устройства») |
| `features/` | по панели: `device` (подключение: список найденных приборов — пока окно открыто, `devices_scan` раз в 2 с по адресу моста из полей окна; выбор и что сохранить — `deviceModel.ts`; скорости, информация, меню каналов), `monitor` (таблица, подсветка, битовая карта, данные сообщения, раздельный приём, диалоги), `stream` (поток, метки, файлы), `transmit` (док, модель задачи, действия), `filters` (панель и диалоги), `tracer` (вид, таблица, таблица ID, проигрыватель, правка, точки останова), `settings`, `files` (диалог файлов). Каждая панель регистрирует свои действия и подставляет компоненты в слоты каркаса (`register.tsx`) |
| `ui/` | примитивы: `Dialog` (модальный: стек окон — Enter/Escape у верхнего, Tab по кругу внутри, остальное приложение `inert`, фокус возвращается туда, откуда окно открыли), `FloatingWindow` (общий порядок окон, z = 500 + индекс — всегда под модальной подложкой), `Menu`/`MenuBar`/`ContextMenu` (один слой всплывающих меню, клавиатура и подменю; закрывается при прокрутке), `Toolbar`, `Tabs`, `Splitter`, `Fields` (флажок, список, ячейки байтов), `grid/VirtualGrid` (виртуальная таблица: рендер только видимых строк, ширины колонок, выделение, контекстное меню, автоследование; высота тела ограничена 15 млн px с пересчётом позиции, потому что Chrome не даёт элементу выше 33,5 млн px — иначе строки дальше ~1,5 млн были бы недостижимы) |
| `i18n/ru.ts` | все подписи интерфейса — формулировки русской локализации десктопа; других строк в компонентах нет |
| `lib/` | чистые функции: `bits.ts`, `timing.ts` (подбор тайминга CAN) |
| `styles/` | токены (светлая и тёмная тема через `data-theme`), базовые стили, компоненты, раскладка |

**Реестр действий** (`core/actions.ts`, аналог `TActionList` десктопа): действие — id,
подпись, подсказка, хоткей, иконка, область (`main` / `tracer` / `global`), `enabled`,
`checked`, `run`. Из одних и тех же действий строятся меню, тулбары, контекстные меню и
хоткеи, поэтому подпись, хоткей и доступность везде совпадают. Хоткеи с Cmd не
перехватываются; в полях ввода работают только F-клавиши; при открытом модальном диалоге
хоткеи окна молчат.

**Высокочастотные данные** идут мимо общего стора, чтобы не перерисовывать весь UI 25 раз
в секунду: строки монитора — `features/monitor/monitorModel.ts` (обновление на месте,
моменты подсветки байтов), поток — `features/stream/streamCache.ts` (страницы по 200
строк, хвост из `capture_tail`), отладчик — `features/tracer/tracerStore.ts`.

**Раскладка и персистентность в браузере**: `ui:*` (вид, режим приёма, панели и их
размеры, недавние трейсы), `grid:<id>:w` (ширины колонок в базовых единицах, масштабируются
по шрифту таблиц), `float:<id>` (положение плавающих окон), `carbus:theme` (применённая
тема и шрифт таблиц — для первого кадра до ответа сервера). Высота дока передачи
ограничивается при отрисовке размером окна (200 px … 65 % рабочей области), сохранённое
значение при этом не меняется.

## Разработка

```bash
# бэкенд
cd backend && python3.12 -m venv .venv            # бэкенду нужен Python 3.10+, системный python3 macOS — 3.9
.venv/bin/pip install -c constraints.txt -e ".[dev]"
.venv/bin/pytest -q                                  # тесты на FakeSession, демо-источнике, поддельном приборе за мостом
.venv/bin/python -m app.demo --port 8765             # http://127.0.0.1:8765, данные и трейсы — в ./data и ./traces
CARBUS_BRIDGE=127.0.0.1:7000 .venv/bin/pytest -q tests/test_carbus_session_smoke.py   # на реальном железе, мост запущен
.venv/bin/python -m app.bridge                       # мост из окружения бэкенда (то же, что ./run-bridge.sh)

# фронт
cd frontend && npm install
npx vitest run                                       # чистые модули и компонентные тесты
npx tsc --noEmit -p .                                # типы: src, tests, scripts
npm run dev                                          # vite dev-сервер, WS и /api проксируются на :8765
npm run build                                        # frontend/dist — его отдаёт бэкенд и копирует Dockerfile
```

Образ собирается в два этапа (`Dockerfile`): `node:22-alpine` собирает фронт (на платформе
сборщика: статика от архитектуры не зависит), `python:3.12-slim`
ставит бэкенд с версиями из `backend/constraints.txt` (сборка воспроизводима; обновлять
осознанно, с прогоном pytest) и отдаёт статику; `docker-compose.yml` публикует
`127.0.0.1:8000`, монтирует `./traces` и `./data`, задаёт `CARBUS_BRIDGE=host.docker.internal:7000`
и `CARBUS_HOST_DIR=${PWD}` (папка, из которой подняли контейнер, — для команды запуска моста).
Готовый образ `ghcr.io/scryptor/carbusmac` (`linux/amd64` и `linux/arm64`) собирает GitHub
Actions (`.github/workflows/docker.yml`) на каждую заливку в `main` (тег `latest` и `sha-…`) и
на теги `v*`; публикует встроенный `GITHUB_TOKEN`, секреты не нужны. В `docker-compose.yml`
у сервиса и `image:`, и `build: .`: `docker compose up` берёт готовый образ, `--build` собирает
свой; если готовый недоступен, compose собирает сам.
`docker-compose.usb.yml` (Linux) дополнительно пробрасывает порт прибора в контейнер
(`devices:`, узел — `CARBUS_USB`, по умолчанию `/dev/ttyACM0`; имя внутри то же, что на хосте,
чтобы pyserial нашёл USB-описатели в `/sys`).
`CARBUS_BRIDGE` — только адрес моста по умолчанию: если в `data/connection.json` уже
сохранён адрес из диалога «Настройки устройства» («Дополнительно»), берётся он. Бэкенду
без Docker мост не нужен — он видит USB сам. Приложение для uvicorn
(`app.server:app`) создаётся при первом обращении, а не при импорте модуля — тесты и
`python -m app.demo --data …` настоящую папку `data/` не трогают.

**Проверка юзабилити.** После UI-изменений — `python -m app.demo` и просмотр в Chrome на
1366×768 и 1366×650 (окно на экране 768) и 1920×1080: ничего не обрезано, нет
горизонтальной прокрутки страницы, текст ≥ 12 px. `frontend/scripts/layout-audit.js` —
функция для `page.evaluate`, возвращает переполнение страницы, обрезанные элементы и
мелкий текст.

**Гифки и скриншоты для README** — `npm run demos` (`frontend/scripts/record-demos.ts`):

- поднимает демо-бэкенд на порту 8766 с временными `data/` и `traces/` (комментарии,
  названия каналов и список передачи заготовлены в скрипте), для каждого сценария — свой
  процесс, чтобы состояние не протекало между сценариями;
- ведёт установленный Google Chrome (headless, через `playwright-core`; браузер Playwright
  не скачивается) по сценариям `connect`, `monitor`, `stream`, `transmit`, `filters`,
  `tracer`, `settings` на 1366×768; курсор и «кольцо» клика рисуются в самой странице,
  потому что скринкаст курсор не снимает;
- кадры берёт скринкастом CDP, GIF собирает сам (`gifenc` + `pngjs`): общая палитра по
  выборке кадров, 10 к/с, неизменившиеся пиксели прозрачны, поэтому размер растёт только
  с изменившейся областью (`scripts/demo-gif.ts` — чистая часть, под тестами);
- пишет `docs/screenshots/<сценарий>.gif` и стоп-кадры `.png` для руководства.
  `npm run demos -- --only monitor,stream` — только выбранные сценарии;
  `CARBUS_PYTHON` — другой python для бэкенда (по умолчанию `backend/.venv/bin/python`),
  `CARBUS_CHROME` — путь к Chrome, если он не в `/Applications`.

**Соглашения.** Подписи — только в `i18n/ru.ts`; хоткеи — с Ctrl, как в десктопе; дроби —
с запятой («12,453»); панели не импортируют друг друга напрямую — через слоты и хуки
каркаса (`slots`, `viewToolbars`, `menuHooks`, `statusHooks`); всё, что можно проверить без
браузера, выносится в чистые модули под Vitest; бэкенд тестируется на `FakeSession`, железо
трогает только smoke-тест.
